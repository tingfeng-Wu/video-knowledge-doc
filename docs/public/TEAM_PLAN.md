# 团队执行计划与当前分工入口

更新：2026-11-02。面向第一次接触代码和实施方案的团队成员。

## 项目要做什么

输入教学视频、在线课程、学术报告或知识解说视频，自动输出可阅读、可检索的结构化文档，包含章节标题、正文、关键帧及说明、关键词或核心结论和时间索引。结项目标是可运行系统、真实评价与强化学习实验，以及软著和答辩材料。

现阶段已有命令行原型。语音识别、视频抽帧与OCR在本地完成；LLM根据带来源信息的文本生成章节和正文；最后导出JSON、Markdown和Word。公开仓库不附带视频、模型权重或API Key，首次使用请按[首页](../../README.md)安装。

## 为什么按这个顺序开发

统一时间轴把ASR文本、页面变化和OCR证据按时间对齐。章节边界有三种计划中的策略：LLM直接分章、规则筛选候选边界、PPO对相同候选边界做保留/丢弃决策。三种策略共用后续正文生成与导出，便于公平比较。

先跑通文档生成，再加视觉信息，随后固定数据和评价，最后训练PPO并集成界面。PPO必须真实训练、保存、加载、测试，并至少生成一个未参与训练的视频文档；实验结果按实际报告，不要求一定超过规则或LLM。没有PPO模型时，系统仍可运行已有LLM路径。

OCR为可选增强，关闭或失败时保留文本主链路。字幕直提后置。视觉描述大模型默认关闭，当前代表帧说明使用确定性规则。最小界面计划使用FastAPI服务端模板，不预设大型前端框架。

## 中期答辩前两周的优先顺序

下面是当前工作的建议顺序，具体人员和日期由团队认领后登记，不预先把任务算到任何成员名下。

1. **先稳定演示**：在第二台机器按README安装，完成离线演示；准备已有成功真实样例的文档、截图和运行记录。现场演示优先使用事先验证过的缓存，避免网络或模型输出影响答辩。
2. **收尾M2**：处理EXPLAINER01重复引用，检查LONG01新文档，明确当前能力及失败边界；真实API复验先记录授权、视频范围和请求上限。
3. **并行准备数据**：核验已有候选链接及使用范围，筛选三类场景；先用少量视频试标、复核，再确定正式15视频，不能先随意分配测试集后反复调参。
4. **形成汇报材料**：画当前实际系统流程，展示输入/输出、缓存复跑、成功与失败案例，明确PPO尚未实现以及后续实验安排。只报告有证据的结果。

中期前不把全部31阶段压成两周完成。优先交付可运行核心、清楚的评价准备及可核验的后续计划；PPO按正式数据和协议的依赖顺序推进。

## 团队可以直接认领什么

| 任务 | 适合参与方式 | 交付物 | 验收方式 |
|---|---|---|---|
| 第二台机器安装 | 熟悉Python基础的成员 | 系统/Python版本、实际命令、成功截图或报错 | 按README完成零API演示 |
| 文档质量检查 | 所有成员 | 章节时间、漏点、错述、配图和排版问题表 | 每条问题能回到视频时间或文档页码 |
| 候选视频复核 | 所有成员 | 来源链接、场景、时长、画面/声音、建议及理由 | 信息完整、去重、来源可追溯 |
| 试标章节边界 | 能认真完整看视频的成员 | 章节起点、标题、理由和复核记录 | 先统一示例和判据，再独立标注与交叉复核 |
| 自动测试/普通缺陷 | 有代码基础的成员 | 最小复现、修复和测试结果 | PR说明问题，相关测试通过 |
| 中期材料 | 所有成员 | 事实清单、流程图、演示步骤、图文案例 | 与实际代码和产物逐项一致 |

候选生成、规则算法、PPO、Schema及预算调整先讨论接口和验收，再开始写代码。不要同时修改同一核心模块，也不要为了演示效果直接篡改正式产物。

## 在GitHub上协作

1. 先读README和本计划，再Fork仓库。
2. 在自己的分支工作。认领前开Issue，写明任务、交付物、验收方法；由团队确认认领，避免重复。
3. 改代码通过Pull Request提交；文档和候选清单也可走PR。视频、API Key、模型和大体积结果经另外确认的渠道共享，禁止提交到Git。
4. PR记录实际运行的测试及未验证项。负责人review后合并；成员不需要了解内部AI开发对话才能参与。
5. 计划、当前事实和新决定通过仓库文档与Issue同步，不只留在个人聊天中。
